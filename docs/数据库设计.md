# 数据库设计

MySQL 8.0.16+ / InnoDB / utf8mb4_0900_ai_ci。单企业、单仓，无仓库表。精确 DDL 以 sql/001_schema.sql 加 sql/003_orders_reservations.sql、sql/004_fulfillment_inventory.sql、sql/005_returns_receipt.sql 为准；001 保留第一阶段基线，002 初始化基础示例数据，003 是第二阶段增量迁移，004 为第三阶段必要字段。不包含 DROP 或清空用户数据；IF NOT EXISTS 不等价于结构迁移，后续变更需另写脚本。

所有 id 为 BIGINT AUTO_INCREMENT 主键；关联字段为 BIGINT。标注可空以外字段均 NOT NULL。默认不级联删除，历史业务数据不物理删除。

## 第一阶段表
| 表 | 字段与类型（除主键） | 约束和索引 |
|---|---|---|
| sys_user | username VARCHAR(50), password_hash VARCHAR(100), display_name VARCHAR(100), enabled BOOLEAN DEFAULT TRUE | username 唯一，哈希不序列化到响应 |
| sys_role | code VARCHAR(30), name VARCHAR(50) | code 唯一，固定 ADMIN/OPERATOR/WAREHOUSE |
| sys_user_role | user_id, role_id | 联合主键，无自增 id；双外键，多对多 |
| product | name VARCHAR(100), description VARCHAR(2000) DEFAULT '', status VARCHAR(20) DEFAULT OFF_SALE | status 枚举检查；(status,id) 支持状态筛选/排序 |
| sku | product_id, code VARCHAR(64), name VARCHAR(100), price DECIMAL(12,2), status VARCHAR(20) | code 唯一；product_id 外键/索引；价格>0，状态检查 |
| stock | sku_id, quantity INT DEFAULT 0, reserved_quantity INT DEFAULT 0 | sku_id 唯一外键，一 SKU 一库存；0≤预占≤实物 |

商品与 SKU 一对多，价格在 SKU，商品不冗余总库存或价格。商品名称包含匹配不盲目增加无效 B-tree 索引。SKU 编码唯一性以数据库约束为准，并发重复写入由全局异常处理返回409，不进行跨层重复查重。MySQL 默认编码大小写不敏感。

库存数量定义：实物 quantity，预占 reserved_quantity，可用量不存储，查询计算差值。新增 SKU 的实物与预占均0，基础示例商品也为0，不创建虚构期初流水。第三阶段通过入库接口增加实物库存并记录RECEIPT流水，业务应用仍不允许直接改库制造库存。正常创建库存与 SKU 为一个事务；绕过应用手动插入 SKU 时必须同时插入对应 stock。

## 订单与后续表

第三阶段已实现sales_order、order_item、stock_movement与shipment；第四阶段启用 return_request 和 return_item。
| 表 | 字段与类型（除主键） | 约束和索引 |
|---|---|---|
| sales_order | order_no VARCHAR(40), status VARCHAR(24), recipient_name VARCHAR(100), recipient_phone VARCHAR(30), recipient_address VARCHAR(500), remark VARCHAR(500) DEFAULT '', total_amount DECIMAL(14,2), created_by, created_at DATETIME DEFAULT CURRENT_TIMESTAMP, completed_at DATETIME 可空 | order_no 唯一；created_by 外键/索引；(status,created_at)、(created_at,id)；金额≥0，状态检查 |
| order_item | order_id, sku_id, product_name VARCHAR(100), sku_code VARCHAR(64), sku_name VARCHAR(100), unit_price DECIMAL(12,2), quantity INT | 双外键；(order_id,sku_id) 唯一；数量>0、单价>0 |
| stock_movement | sku_id, order_id 可空, movement_type VARCHAR(24), quantity_delta INT, reserved_delta INT, quantity_after INT, reserved_after INT, remark VARCHAR(500) DEFAULT '', business_key VARCHAR(100), operator_id, created_at DATETIME DEFAULT CURRENT_TIMESTAMP | business_key 唯一；SKU、操作人、可空订单外键；(sku_id,created_at)、(order_id,created_at)；至少一个 delta 非0，变更后余额不越界 |
| shipment | order_id, status VARCHAR(20), carrier VARCHAR(80) 可空, tracking_no VARCHAR(80) 可空, shipped_by 可空, shipped_at DATETIME 可空 | order_id 唯一外键；shipped_by 外键；状态检查 |
| return_request | return_no VARCHAR(40), order_id, status VARCHAR(24), reason VARCHAR(500), created_by, created_at DATETIME DEFAULT CURRENT_TIMESTAMP | return_no 唯一；双外键；order_id/status 索引及审核人、验收人外键；状态检查 |
| return_item | return_id, order_item_id, quantity INT, refund_amount DECIMAL(14,2) | 双外键；(return_id,order_item_id) 唯一，order_item_id 索引；数量>0、金额≥0 |

订单总金额由价格快照×数量求和，不从客户端信任总额；无浮点金额。退货明细金额保存预计退款金额，不表示支付已执行。表间外键保证存在性；当前实现由服务端选择原订单明细并核对已完成状态、限制累计退货数量、计算订单总额；发货资料由输入校验保证，相关写入在业务事务内完成。

## 状态与一致性设计
订单：PENDING_PAYMENT→PENDING_SHIPMENT→SHIPPED→COMPLETED；仅PENDING_PAYMENT/PENDING_SHIPMENT可取消到CANCELED。发货后不可取消，确认收货仅后台模拟、不接真实物流平台。模拟付款不接真实支付，取消不处理资金。本模型一次完整发货，每订单唯一 shipment，其状态 PENDING→SHIPPED。
退货从 PENDING_REVIEW 进入 REJECTED 或 PENDING_RECEIPT，验收入库后进入 COMPLETED。新申请仅包含一条明细。

库存流水类型 RECEIPT/RESERVE/RELEASE/SHIP/RETURN。RECEIPT 与 RETURN 增实物；RESERVE 增预占；RELEASE 减预占；SHIP 同时减实物和预占。与余额写入同事务。创建订单实际采用 UPDATE stock SET reserved_quantity=reserved_quantity+? WHERE sku_id=? AND quantity-reserved_quantity>=?，以受影响行数判定成功。取消先条件更新订单状态，再用 reserved_quantity>=? 的条件更新释放库存。不能用之前查到的库存作为并发保证。business_key 使用 RESERVE:order_item_id / RELEASE:order_item_id / SHIP:order_item_id，订单状态限制重复操作，唯一键阻止重复流水。按SKU ID升序操作库存，减少交叉锁顺序。条件更新后用 FOR UPDATE 当前读取得流水余额，避免MySQL REPEATABLE READ旧快照影响流水。

角色与权限不单独建动态 permission 表：固定权限矩阵映射到 Spring Security @PreAuthorize。sys_user_role 支持多角色，不允许客户端伪造角色。身份禁用和角色变更按请求重新读取。

## 003增量迁移注意事项
执行前备份并停写，使用具有ALTER/CREATE ROUTINE权限的迁移账号，不能使用只授权CRUD的应用账号。003不删除业务行，不重建表，转换旧CANCELLED→CANCELED，新增remark、product_name、可空order_id和索引，替换订单状态检查约束。

如旧库存在CREATED/CONFIRMED活动订单，脚本在修改任何业务表之前SIGNAL中止；第一阶段未提供订单入口，人工旧数据的预占含义无法自动推断，需先核对实际库存与业务再迁移。没有擅自把旧未预占订单转换成新待付款订单。失败后辅助存储过程可能保留，核对原因后可DROP PROCEDURE orderflow_phase2_migrate再重新执行。

旧订单行新增商品名称只能按关联商品当前名称补齐；不宣称恢复了过去未保存的历史名称。原单价与订单金额不修改。既有非订单库存流水order_id保持NULL；新订单流水由应用始终写入order_id。

MySQL DDL隐式提交，003只执行一次，非全脚本原子事务；任一步DDL失败时先检查已完成的变更，不盲目重跑。不通过回滚迁移删除新产生的订单或流水；出问题优先修复，必要时使用维护窗口备份恢复。

## 004第三阶段增量迁移
只新增sales_order.completed_at（可空）和stock_movement.remark（VARCHAR(500)、默认空字符串），不修改旧状态、金额、余额或流水delta。不新建库存体系；shipment已有order_id唯一约束及物流、发货人、发货时间字段，直接复用。已有第二阶段库只执行004，不能重跑初始化或003。执行前备份停写，DDL隐式提交且仅执行一次，发生中途失败时先确认列是否已添加再处理。

发货事务先用WHERE status='PENDING_SHIPMENT'条件更新订单；成功者按SKU升序同时扣quantity与reserved_quantity，再写SHIP流水和唯一shipment。reserved_quantity>=发货数量结合既有quantity>=reserved_quantity约束保证不越界。可用库存差值不变。例如100/20/80发5件后为95/15/80。任何SKU、物流记录或流水写入失败，全事务回滚。发货与取消竞争同一订单行，不能两者都成功。

完成订单只用WHERE status='SHIPPED'条件更新为COMPLETED并写completed_at，不调用库存Mapper。重复发货、取消或确认收货返回409，无重复库存影响。物流信息通过订单详情返回shipment，历史未发货/已完成时间无法推断时保留NULL，不虚构时间。

库存入库以条件UPDATE增加quantity，判断INT上限，不改变reserved_quantity；入库与RECEIPT流水同事务。正整数边界由Bean Validation及Jackson禁止浮点转整数负责，不在Service重复基础校验。每次入库是独立作业，流水主键作为记录编号，business_key为RECEIPT:UUID，order_id为空；订单流水关联真实订单并使用类型+订单行ID业务键。备注与操作人可追溯，不增加通用入库单/采购框架。

## 005 售后迁移与并发约束

005 为 return_request 增加 reviewed_by、reviewed_at、rejection_reason、received_by、received_at、receipt_remark、updated_at。历史 REQUESTED、APPROVED、RECEIVED 分别映射为 PENDING_REVIEW、PENDING_RECEIPT、COMPLETED，REJECTED 保留。历史验收与审核信息无法从旧字段推断时保留空值。

复用 return_item 的 order_item_id 外键关联原订单明细，SKU 通过该明细获取。refund_amount 表示预计金额，使用成交价快照计算。为 order_item_id 增加索引，查询累计数量时排除 REJECTED。

申请事务以 READ COMMITTED 在原订单明细行上执行 FOR UPDATE，取得锁后重新读取累计占用并判断剩余量。审核、验收均通过状态条件更新决定唯一胜者。验收沿用库存容量检查、原子实物增加和流水写入，RETURN 流水的 reserved_delta 为 0，business_key 为 RETURN:售后明细ID，可追溯到售后和原订单。状态、库存及流水同事务，原订单保持 COMPLETED。
